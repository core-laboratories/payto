# QR Ph implementation report — 2026-09-16

1. **Authoritative research:** BSP national QR overview and P2P/P2M FAQs; BancNet QR Ph service announcements; participant PayMongo MPM and QR Ph acceptance documentation. Searches of BSP, PPMI, BancNet and participant material did not establish a complete public Philippine wire profile. Source links and architecture are in [PAYQR.md](PAYQR.md#philippine-qr-ph-payment-data).
2. **Verified concepts:** P2P, P2M, InstaPay interoperability; participant PHP static/dynamic payment flows. Provider-specific centavo API units are not PayTo amount units.
3. **Unverified fields:** primary destination grammar for each mode, institution IDs, routing/account templates, native merchant fields, additional-data tags, Philippine CRC profile and conformance vectors. No invented fields or national validation claims.
4. **Identifier:** existing opaque issuer envelope (1–128 Unicode letters/digits or `_.@+-`, excluding dot segments). This is a URI safety constraint, not QR Ph account validation; amber UI feedback remains. Issuer enrollment cannot be verified locally.
5. **P2P:** optional `payment-mode=p2p` in generic QR parameters, exposed as `paymentMode` on Payto/JSON.
6. **P2M:** optional `payment-mode=p2m`, same portable envelope; this does not assert identical native destinations. No mode-specific routing form until verified.
7. **Static/dynamic:** optional `qr-type` and `qrType` property. Existing profile requires an amount for dynamic. Static URI data is preserved even with a generic suggested amount; no native mapping is asserted. Participant static APIs may prohibit amount. No mandates or recurring semantics are introduced.
8. **Zod:** Philippine country/scheme schema validates portable identifier, PHP, decimal amount, mode/type enums, controls and lengths. No unsupported P2P/P2M discriminated native schema. Dynamic amount is conditional. Native validation remains separate from portable URI validation.
9. **Canonical URI:** `payto://qr/ph/{identifier}`; country selects `qrph`; no repeated scheme. Sorted query serialization, percent escaping, receiver-name/reference preservation and atomic property setters.
10. **Native encoder:** unavailable under the brief's explicit fallback rule; no guessed implementation.
11. **Native decoder:** unavailable; cannot safely identify native QR Ph from country/currency alone. PayTo URI decoding works.
12. **EMV/TLV:** no new speculative Philippine utilities. Existing website utilities for other countries unchanged.
13. **CRC:** no Philippine CRC implementation or claim of correctness.
14. **Vectors:** no authoritative native conformance vectors established. Tests use clearly illustrative PayTo URI fixtures, not fabricated native vectors.
15. **Website files:** validator, PayQrConstructor, new qrph unit tests, pass-api tests, PayQR Playwright test, PAYQR documentation and this report. Existing PayPass resolver and API continue to share barcode data.
16. **TypeScript files:** src/payqr/registry.ts, src/index.ts, test/payqr.test.ts, shared test/fixtures/payqr.json, README.md; generated build output updated locally.
17. **Dart files:** lib/src/payqr.dart, lib/src/payto.dart, lib/src/models/payto_json.dart, test/payqr_contract.dart, shared test/fixtures/payqr.json, README.md.
18. **Tests added:** both modes/types, PHP amounts, invalid precision/currency/zero/exponent, malformed URI/escaping, duplicate modes, control characters, getter/setter/JSON parity, atomic rejection, 8192-character limit; Zod/native-unavailable/portable resolver and browser flow. Existing other-country and non-QR tests retained.
19. **Test results:** website 165 unit tests and 17 Playwright tests passed; TypeScript 148 tests passed; Flutter 138 tests passed. Both JSON/form API tests cover Apple/Google portable PH data and reject native before signing (wallet builders mocked). Production build passed as the Playwright web-server prerequisite.

Website changed validator/component/test/report files formatted. Native preview stays hidden; the constructor explains availability outside the barcode. Selecting PayTo renders the portable link and enables wallet passes through existing form/API handling. No bank-network connectivity, image dependencies in data libraries, payment settlement or enrollment.
